# DT Collector: project brief

Start a new session with this file. It describes a new, separate project:
a public, central server that receives hardware test reports from
SwarmDialer instances and lets a few admins browse and compare them.

SwarmDialer (the test tool that produces the reports) is a separate,
existing project: `~/claude/SwarmDialer`, GitHub `galijas/swarmdialer`.
The report format and upload API below are the contract between the
two; change them in both projects together.

## Purpose

SwarmDialer runs a standardized call load test against PBXware VPSs
running on one SERVERware host, while collecting that host's hardware
metrics from SERVERware's Prometheus. When the whole test script
finishes, SwarmDialer uploads one report to DT Collector. DT Collector
stores reports from every SwarmDialer deployment (Bicom's network,
private networks and public SERVERware sites) so hosts and hardware can
be compared side by side.

## Deployment

- Ubuntu server on Bicom's own publicly reachable hosting (SERVERware in
  the background). Public, since SwarmDialers on other networks must
  reach it to upload.
- Same install style as SwarmDialer: `git clone` + `sudo ./install.sh`,
  runs as a systemd service.
- The install script prompts for:
  - the server's public DNS name (an existing DNS A record pointing at
    the server), and
  - an email address,
  and uses them to obtain a Let's Encrypt certificate (with automatic
  renewal).
- Suggested stack, matching SwarmDialer: a single Go binary with an
  embedded web UI and SQLite. Not fixed; decide in the new project.

## Security (agreed scope; keep to this)

1. **HTTPS with a real certificate** (Let's Encrypt, from the DNS name and
   email given at install). HTTP only redirects to HTTPS.
2. **Two separate ways in:**
   - **Admin interface:** a few local admin accounts, passwords stored
     hashed (bcrypt or argon2). No two-factor login. Admins browse and
     compare reports and manage upload API keys.
   - **Upload API:** used only by SwarmDialer, authenticated with upload
     API keys (below). An upload key can only upload reports: it can't
     read, list or delete anything, and can't log into the interface.
3. **Upload API keys:** created by an admin in the interface, shown once
   at creation, stored hashed, revocable individually, with "last used"
   shown. SwarmDialer asks for the key when the user adds the SERVERware
   site in its Setup Wizard.
4. **Server hardening:** only 443 (plus 80 for the redirect and Let's
   Encrypt, and SSH) open; the app runs as its own unprivileged user under
   systemd, not root; regular database backups.

Reports never contain secrets, internal IPs or host names (see below).

## Upload API (contract with SwarmDialer)

Base URL: `https://<dns-name>`

Authentication on every call: header `Authorization: Bearer <upload key>`.
Suggested key format: `dtk_` + 40+ random characters.

- `GET /api/v1/ping`: checks a key. `200 {"status":"ok"}` if valid,
  `401` if not. SwarmDialer calls this when the user enters the key, to
  confirm it before saving.
- `POST /api/v1/reports`: uploads one report (JSON body, see below;
  `Content-Encoding: gzip` allowed).
  - `201 {"id": "<report_id>"}`: stored.
  - `200 {"id": "<report_id>", "duplicate": true}`: a report with this
    `report_id` already exists (SwarmDialer retries uploads, so this must
    be idempotent).
  - `400 {"error": "..."}`: fails validation (the message says which
    field).
  - `401`: missing, invalid or revoked key.
  - `413`: body too large (suggested limit: 20 MB).

SwarmDialer verifies the server's certificate (no self-signed
acceptance), keeps a local copy of every report, and retries a failed
upload.

Rules:
- **No secrets, internal IPs or host names** anywhere in a report: no API
  keys, passwords, VPS descriptions, IP addresses, VPS or host names.
  Only hardware details, versions and results. SwarmDialer builds
  reports from an explicit allowlist of fields.
- Only complete runs of the whole test script are uploaded.
- Reports are comparable only when `profile.name` and `profile.version`
  match. The interface should compare within one profile version only.

## The standardized test script (profile "standard", version 1)

All three VPSs (SwarmDialer, PBXware MT, PBXware CC) run on the same
SERVERware host; SwarmDialer checks this before testing. Calls are
remote calls MT → CC over the SIP trunk. The PBXware license allows 512
concurrent calls, which is the target.

Ramp tests (calls last about 10 minutes, ramped up to 512 concurrent):
stop if the host or a VPS hits 100% CPU or RAM and note the concurrent
call count reached; otherwise hold at 512 calls for 1 minute, record the
hardware usage, stop, and go to the next test.

1. No recording, low-cost codec
2. No recording, high-cost codec (transcoding: e.g. caller opus, callee ulaw)
3. Mono recording, low-cost codec
4. Mono recording, high-cost codec
5. Stereo recording, low-cost codec
6. Stereo recording, high-cost codec

Then a **rolling test**: stereo recording, 1-minute calls, each finished
call replaced immediately, dial rate raised step by step up to 512
concurrent calls (about 8.5 calls per second), to load MP3 conversion.
Reports its MP3 conversion delay and its RAM disk fill estimate.

Each test has a 1-minute idle baseline before and a cooldown after.
Stereo recording fills the 512 MB recording RAM disk at about 29 KB/s
per call; when full, calls continue but recordings are cut off. This is
reported (as an estimate) as a limitation, not treated as a failure.

## What the interface should show (first version)

- List of reports (date, hardware summary, SERVERware/PBXware versions,
  profile), filterable.
- One report: per-test results and the time series as charts.
- Compare 2 or more reports of the same profile version: per test, side
  by side (max concurrent calls, stop reason, host CPU/RAM at target,
  Asterisk CPU, setup time, MOS, MP3 conversion delay), with charts
  overlaid.
- Admin: manage admin accounts and upload API keys.

## Context from SwarmDialer (for reference)

- SERVERware 5.2 Prometheus runs on the controller at
  `https://<controller>/prometheus` and accepts the SERVERware API token
  (`SW-API-Token` header). Metrics: node exporter (hosts), per-VPS
  process metrics (`namedprocess_*`, per process group, e.g. asterisk),
  SRW exporter (`srw_active_calls`, `srw_vps_info` mapping VPS to host).
- The time series in a report come from those metrics, sampled over each
  test's time range.
